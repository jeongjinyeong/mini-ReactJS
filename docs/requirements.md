# mini-react 요구사항

이번 주 목표는 브라우저에서 두 UI 트리의 차이를 구하고, **실제 영역에서 바뀐 부분만 갱신하는 것**이다. Phase 2에서는 HTML 편집 대신 상태 변경이 다음 UI 트리를 만든다.

좋아요 하나를 눌러 버튼, 게시글의 카운트, 사이드바의 카운트를 각각 찾아 수정하다 보면 어느 한 곳을 놓치기 쉽다. 화면의 다음 모습을 한 번 정의하고, 실제로 어떤 DOM 노드를 바꿀지는 공통 코드에 맡겨 보자. 이 프로젝트에서 Phase 1은 그 가정을 눈으로 확인하는 실험이다.

## 공통 제약

- 브라우저에서 동작하는 HTML, CSS, TypeScript를 사용한다. 외부 UI 프레임워크는 사용하지 않는다.
- 각 단계의 데모에서 사용자의 편집 또는 클릭으로 화면이 변해야 한다. 핵심 모듈은 단위 테스트, 사용 흐름은 브라우저 기능 테스트로 검증한다.
- 필요한 DOM 갱신의 범위는 [설계](architecture.md)의 노드 대응 규칙을 따른다. DOM 변경이 줄었는지는 확인하되 속도 향상은 별도로 측정한다.

## Phase 1 · 이번 주

| ID | 기능 | 인수 기준 |
| --- | --- | --- |
| FR-001 | DOM → Virtual DOM | HTML 요소, 속성, 텍스트와 공백의 순서를 담는다. 읽기 과정에서 원본을 수정하지 않으며 지원하는 input의 현재 값도 읽는다. |
| FR-002 | Virtual DOM → DOM | 중첩 요소, 혼합 텍스트, 빈 요소, 지원 속성 및 input 상태가 동일한 DOM을 생성한다. |
| FR-003 | Diff | 추가, 삭제, 교체, 이동, 텍스트 변경, 속성·프로퍼티 변경을 구분한다. `key`가 있는 형제는 `key`로, 없는 형제는 위치로 대응시킨다. 형제 사이의 `key` 중복은 오류다. 같은 트리의 변경 목록은 비어 있다. |
| FR-004 | Patch | 변경 대상만 수정하며, 변경 대상 밖 노드의 객체 참조가 유지된다. |
| FR-005 | 데모 초기화 | 실제 영역의 샘플 DOM을 스냅샷으로 저장한다. 그 스냅샷으로 테스트 영역의 HTML 편집기와 미리보기를 채운다. |
| FR-006 | 변경 적용 | 테스트 영역의 HTML을 편집하면 미리보기에 반영된다. Patch를 누르면 현재 초안을 변환하고 변경점만 실제 영역에 반영한다. |
| FR-007 | 변경 이력 | 성공한 변경의 Virtual DOM을 최대 10개 저장한다. 초기 상태도 포함한다. 변경이 없는 Patch는 이력을 추가하지 않는다. 이력 개수와 현재 위치를 페이지에 표시한다. |
| FR-008 | 뒤로·앞으로 | 이전 또는 다음 스냅샷으로 한 칸 이동한다. 처음과 마지막에서는 해당 이동 버튼을 비활성화한다. |
| FR-009 | 이력 복원 | 실제 영역은 Diff와 Patch로, 테스트 영역은 선택한 스냅샷으로 복원한다. 미적용 초안은 복원한 상태로 대체한다. |
| FR-009a | 화면 구성과 변경 표시 | 페이지에 HTML 편집기와 Patch 버튼, Real DOM, Virtual DOM을 보여준다. Patch나 이력 이동으로 바뀐 영역은 2초간 빨갛게 표시한다. |

### 편집과 이력의 동작 기준

- MVP에서 HTML 편집기가 유일한 편집 경로다. 실제 영역과 미리보기는 표시 전용이다. 편집기에서 `<input value="정글">`로 바꾸어 적용하면 실제 입력창은 `정글`을 표시한다.
- HTML 편집기가 초안의 기준이다. 실제 영역은 유효한 초안에 Patch를 누르거나 이력을 이동할 때 바뀐다. 초기 상태와 반영된 스냅샷의 이력은 페이지가 열린 동안 메모리에 유지한다.
- 뒤로 간 뒤 **변경이 있는** Patch에 성공하면 현재 위치의 이후 이력을 제거한 뒤 새 스냅샷을 저장한다. 변경이 없는 Patch는 앞으로 갈 수 있는 이력도 그대로 둔다.
- 편집 범위는 일반 HTML 요소·텍스트와 지정된 속성이다. 빈 입력은 빈 트리로 적용한다. 브라우저가 보정한 파싱 결과를 기준으로 비교한다. 주석은 생략하고 공백 텍스트는 보존한다.
- 지원하지 않는 요소 또는 속성이 파싱 결과에 있으면 테스트 영역에 이유를 표시한다. 실제 영역과 이력은 유지하고, 미리보기는 마지막으로 유효했던 상태를 유지한다. 허용 범위는 [설계](architecture.md)에서 정의한다.

- 초안을 편집하는 동안에는 이력이 바뀌지 않는다. 유효한 초안 뒤에 잘못된 입력이 들어와도 Patch는 마지막 미리보기 대신 **현재 편집기 내용**을 검사한다.
- 유효한 초안으로 다시 편집하거나 이력 이동에 성공하면 이전 입력 오류 안내를 지운다.

## Phase 2 · 후속 단계

| ID | 기능 | 인수 기준 |
| --- | --- | --- |
| FR-010 | 함수형 컴포넌트 | 함수로 UI를 정의하고 여러 함수를 조합할 수 있다. |
| FR-011 | 컴포넌트 관리 | 루트를 감싼 `FunctionComponent`가 `hooks` 배열과 `mount()`, `update()`를 가진다. |
| FR-012 | Props | 루트가 자식에 표시할 값과 이벤트 콜백을 props로 전달한다. |
| FR-013–015 | useState | 함수가 재실행되어도 값이 유지된다. setter로 상태를 바꾸면 별도 Patch 버튼 없이 화면이 갱신된다. |
| FR-016 | 엔진 연계 | 상태 변경으로 새 Virtual DOM을 계산하고 Phase 1의 Diff와 Patch로 실제 DOM을 갱신한다. |
| FR-017 | useEffect | 첫 DOM 반영 이후 실행된다. 의존성이 바뀌면 기존 정리 함수를 실행한 뒤 효과를 다시 실행한다. |
| FR-018 | useMemo | 의존성이 같으면 계산 결과를 재사용하고, 바뀌면 다시 계산한다. |
| FR-019–020 | 루트 상태·순수 자식 | Hook은 루트 컴포넌트 본문의 최상위에서 호출한다. 자식은 자체 Hook이나 상태 없이 받은 props로 UI를 반환한다. |
| FR-021 | Batching | 선택. 연속 상태 변경을 모아서 DOM 반영 횟수를 줄인다. |

Phase 2 데모에서는 버튼 클릭이나 입력 하나로 루트 상태를 변경하고, 같은 상태를 읽는 두 자식의 표시가 함께 바뀌는지 확인한다.

## 선택 과제

기능이 검증된 뒤 데모에 **마지막 Patch의 변경 종류와 개수**를 표시할 수 있다. 예를 들어 “텍스트 1개 변경”을 표시해, 최종 화면과 그 화면을 만들기 위해 수행한 DOM 작업을 함께 보여준다.
