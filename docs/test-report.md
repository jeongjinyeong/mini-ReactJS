# Phase 1 테스트 결과 보고서

이 보고서는 `feat/dom-to-vnode` 병합 전 Phase 1 작업 트리의 실행 기록이다.
현재 `LJM-testpage`의 Phase 2 또는 병합 후 전체 검증 결과를 의미하지 않는다.
현재 실행 방법은 [테스트 안내](../tests/README.md)를 참고한다.

실행일: 2026-11-11. 대상은 해당 날짜의 **당시 작업 트리**다.
작업 시작 전부터 추적 파일 12개에 변경 표시가 있었으므로 HEAD만을 대상으로 한 결과가 아니다.
이번 작업은 테스트와 문서에 한정했으며 엔진이나 데모의 기능을 수정하지 않았다.

## 1. 환경과 재현

| 항목 | 실행 환경 |
|---|---|
| 호스트 | Linux x64, WSL2 |
| 브라우저 테스트 런타임 | Windows Node.js v24.16.0 |
| 브라우저 | Windows Google Chrome 157.0.8103.50, headless |
| 추가 확인 런타임 | Bun 1.4.4 |
| 테스트 진입점 | standalone: 임베드 모듈 단독 데모 / modules: 개발용 ES 모듈 |

WSL 저장소 루트에서 실행한 회귀 명령:

```sh
"/mnt/c/Program Files/nodejs/node.exe" tests/run-phase1-tests.mjs
```

일반적인 Node.js 환경에서는 다음 명령과 같다.

```sh
node tests/run-phase1-tests.mjs
```

실행기는 각 모드에 새 Chrome 프로필과 임시 HTML을 만들고 실제 DOM을 검사한다.
따라서 DOM 모형만을 사용한 테스트가 아니다.

## 2. 단위·통합·시나리오 결과

| 분류 | 기존 고유 사례 | 추가 고유 사례 | 최종 고유 사례 | standalone | modules |
|---|---:|---:|---:|---:|---:|
| Unit | 0 | 5 | 5 | 5 통과 | 5 통과 |
| Integration | 8 | 2 | 10 | 10 통과 | 10 통과 |
| Scenario | 9 | 3 | 12 | 12 통과 | 12 통과 |
| 합계 | 17 | 10 | **27** | **27/27** | **27/27** |

회귀 명령의 최종 종료 코드는 **0**이다.
27개의 서로 다른 사례를 두 진입점에서 실행한 **54회 통과**이며,
54개의 서로 다른 테스트가 생겼다는 의미가 아니다.
전체 항목과 기대 결과는 [테스트 목록](../tests/TEST-CASES.md)에 있다.

주요 검증 범위:

- Unit: 주석 제외와 텍스트 경계, key/체크박스 DOM 생성, 빈 자식 REMOVE,
  속성 변경 분류, 잘못된 Patch 경로 오류.
- Integration: DOM/VNode 왕복, no-op 쓰기 없음, 속성·텍스트 최소 갱신,
  삽입·삭제·교체, 키 재정렬 중 객체 정체성, 이동과 텍스트 변경의 동시 반영.
- Scenario: 실제 편집·Patch 버튼, 입력 거부와 접근성 오류 상태,
  undo/redo와 분기 이력, 이력 10개 상한, 공백/CR 복원, 강조 애니메이션,
  체크박스, 빈 입력과 여러 최상위 노드.

추가 전 기준 실행도 standalone 17/17, modules 17/17, 종료 코드 0이었다.
추가 테스트의 첫 실행에서는 주석 앞뒤 텍스트가 합쳐진다고 잘못 기대한 신규 테스트 1건이
각 모드에서 실패했다. `fromDOM`은 주석을 생략하되 텍스트 경계는 보존하며,
병합은 데모 파서의 `normalize()` 책임이라는 소스를 확인해 **신규 테스트의 기대값**을 정정했다.
기존 테스트를 완화하거나 런타임을 통과하도록 바꾼 것은 아니다.

검토 중에는 새 identity 검증이 `undefined === undefined`로 거짓 통과할 수 있는 경로도 바로잡았다.
최종 테스트는 실제 `ul.children`의 기존 노드 참조와 이동 후 참조를 비교한다.
새 시나리오의 문구 고정 검증도 제거하고 `aria-invalid`, 오류 가시성,
유효한 미리보기 보존·복구를 검증하도록 변경했다.

## 3. 스킬 기반 퍼징 결과

`harness-writing` 스킬의 결정적 seed, 구조 인식 입력, 크기 제한, 반복별 상태 초기화,
비교 오라클 원칙을 실제 Chrome DOM에서 적용했다.
네이티브 C/C++ 하네스를 이 JavaScript 저장소에 억지로 연결하지 않았으며,
**커버리지 유도 방식이 아닌 생성형 퍼징**으로 분류한다.

| seed | 최종 하네스 실행 횟수 | 통과 | 실패 |
|---:|---:|---:|---:|
| 0 | 1,000 | 1,000 | 0 |
| 1 | 1,000 | 1,000 | 0 |
| 42 | 1,000 | 1,000 | 0 |
| 2026 | 1,000 | 1,000 | 0 |
| 20261111 | 1,000 | 1,000 | 0 |
| 합계 | **5,000** | **5,000** | **0** |

주 조정자가 최종 하네스로 직접 실행한 명령이며 종료 코드는 **0**이다.

```sh
for seed in 0 1 42 2026 20261111; do
  "/mnt/c/Program Files/nodejs/node.exe" tests/run-fuzz.mjs "$seed" 1000 || exit
done
```

각 반복에서 F1 왕복, F2 no-op diff, F3 증분 결과와 새 렌더링 비교,
F4 무작위 키 순열의 순서·자식 수·객체 정체성을 검사했다.
생성기의 기본 최대 깊이는 3, 깊이별 최대 자식 수는 4/3/2, 최대 속성 수는 2다.
변형 시에도 남은 깊이와 기존 형제 key를 반영한다.
키 순열은 2~4개의 고유 key를 가진 별도 평면 목록으로 생성하여 부모 간 동일 key를 혼동하지 않는다.

이전 하네스에서는 키 객체의 정체성만 보고 순서를 검증하지 않는 약점을 발견해 고쳤다.
위 표는 **수정 이후 실행만** 집계하며, 수정 전 시험 실행 300회나 하위 에이전트의 중간 실행을 더하지 않았다.
실패가 없었으므로 저장할 실패 입력은 없었다. 실패 시에는 seed·반복 번호·오라클·관련 입력을 출력한다.
긴 트리, 모든 HTML 파싱 규칙, 데모의 입력 검증 및 오류 입력 공간까지 퍼징했다는 뜻은 아니다.

별도 변이용 브라우저 기준 테스트도 `node tests/run-mutation-tests.mjs`로 직접 실행해
**11/11 통과, 종료 코드 0**을 확인했다. 이는 정상 원본의 기준 결과이며 변이 점수가 아니다.

## 4. 변이 테스트 결과

Stryker 10.1.1을 사용하여 속성 변경의 두 구간을 대상으로 캠페인을 완료했다.
전용 `tests/mutation-unit-tests.js`의 11개 브라우저 기준 테스트를 사용한다.
단위·통합·시나리오 회귀 27개 전체를 변이 테스트한 결과가 아니다.

| 대상 | 생성 변이 | 검출(Killed) | 생존(Survived) | Timeout | Error | 점수 |
|---|---:|---:|---:|---:|---:|---:|
| `diff.js:12-19` (`diffProps`) | 18 | 12 | 6 | 0 | 0 | 66.67% |
| `patch.js:65-68` (`UPDATE_PROPS`) | 4 | 2 | 2 | 0 | 0 | 50.00% |
| 합계 | **22** | **14** | **8** | **0** | **0** | **63.64%** |

주 조정자가 최종 설정 그대로 아래 명령을 실행해 **종료 코드 0, 약 16초**를 확인했다.

```sh
cmd.exe /c "stryker run tests/stryker.config.json --logLevel info"
```

정상 원본으로 기준 테스트가 통과한 뒤 변이별 실행을 수행했다.
Node 환경의 활성 변이 ID를 브라우저의 `window.__stryker__.activeMutant`로
모듈 로딩 전에 전달한다. 그렇지 않으면 브라우저에서 변이가 활성화되지 않는다.

[JSON 원본](../tests/mutation-constrained-report.json)의 22개 상태를 직접 집계했으며,
Killed 14개 모두 `statusReason`에 실제 11개 suite의 FAIL 결과가 있음을 확인했다.
JSON에 기록된 원본 코드도 현재 `diff.js`·`patch.js`와 줄바꿈 정규화 후 일치했다.
실행기 오류를 테스트 실패로 간주해 점수를 올렸다는 근거는 없으며,
최종 구간에는 timeout/error 상태가 없다.

생존 8개는 변경 없는 속성의 불필요한 쓰기, 추가·삭제 속성 선택,
실제 속성 제거, 변경 대상 반환값을 전용 suite가 충분히 확인하지 못한 경우다.
`affected.add(target)` 제거도 강조 대상 반환값을 바꾸므로 동등 변이가 아니다.
모든 생존 변이의 JSON ID와 추가할 검증은 [상세 분석](testing-analysis.md)에 기록했다.
점수 63.64%를 저장소 전체 커버리지나 원본 코드의 결함 비율로 해석하면 안 된다.

## 5. 결과의 해석과 한계

- 위 결과는 명시한 브라우저와 입력 범위에서의 회귀 증거다. 전체 입력 공간의 정확성이나 React 호환성을 증명하지 않는다.
- statement/branch coverage를 계측하지 않았다. 통과율을 코드 커버리지로 해석하면 안 된다.
- Firefox/Safari, 터치·키보드 접근성 전체, 큰 트리 성능·스택 한계, SSR/hydration은 검증하지 않았다.
- 강조 테스트는 애니메이션을 정지하고 재생 위치를 지정한다. 2초를 실제로 기다리는 고정 sleep에 의존하지 않는다.
- 이 작업으로 UI 스타일을 변경하지 않았다. 시나리오는 실제 데모를 조작하지만 별도의 반응형 시각 품질 인증은 아니다.
- TypeScript 및 Biome LSP 실행 파일이 설치되지 않아 LSP 정적 진단은 실행하지 못했다.
  실제 Chrome의 ES 모듈 로딩·실행 결과를 확인했으며 정적 타입 검사 통과를 주장하지 않는다.
- Windows Node.js의 `--check`로 회귀 테스트와 퍼징·변이 테스트의 브라우저 코드 및 실행기
  5개 파일을 검사했고 종료 코드 0을 확인했다.
- 단독 HTML에 포함된 `vnode.js`, `diff.js`, `patch.js`, `demo.js`는
  CRLF/LF를 정규화했을 때 현재 소스와 일치함을 확인했다.
  런타임 변경이 없어 생성 HTML을 다시 쓰는 빌드는 실행하지 않았다.

React와의 구현 및 Diff 차이는 [비교 문서](react-comparison.md)에 정리했다.
