# mini-react 테스트 계획

Phase 1의 합격 조건은 **바뀐 화면이 맞고, 그대로인 DOM 노드도 유지되는 것**이다. HTML 문자열 비교만으로는 전체를 다시 만든 구현도 통과하므로 결과 구조와 노드 참조를 함께 확인한다.

현재 DOM → VNode 변환은 구현되어 있고, `toDOM`은 선언만 있는 상태다. 실행 가능한 자동 테스트와 실제 브라우저 변환 검증은 아직 없다. 이 문서의 케이스는 통과 기록이 아니라 검증 계획이다. 첫 자동 테스트는 브라우저 테스트 페이지에서 TypeScript와 작은 assertion 함수로 시작한다. 페이지에서 실행 결과와 실패 케이스를 확인할 수 있게 한다.

## 다음 검증 순서

1. P1-01로 기존 `fromDOM`의 중첩 요소·혼합 텍스트·공백·주석 제외·원본 보존을 확인한다. 주석과 달리 `Document`·`DocumentFragment` 같은 미지원 노드 종류는 오류여야 한다.
2. P1-07 중 스냅샷 부분으로 HTML 기본 속성과 현재 input 프로퍼티를 따로 읽는지 확인한다. 체크 해제 상태인 `false`도 포함한다.
3. `toDOM` 구현 후 P1-02로 `fromDOM(toDOM(vnode))`가 지원하는 정규화 VNode와 같은지 확인한다. 생성 노드가 분리되어 있고 입력 VNode가 변하지 않는지도 확인한다. VTree는 노드별로 생성·재독해한 배열을 비교한다.
4. Diff·Patch 구현 후 P1-07의 나머지 적용 검증과 P1-03 이후 관련 케이스로 확장한다.

## 1. Phase 1 단위·통합 테스트

| ID | 범위 | 입력과 기대 결과 |
| --- | --- | --- |
| P1-01 | DOM 변환 · FR-001 | 중첩된 요소, 앞뒤 텍스트, 줄바꿈과 공백, 주석, 빈 요소를 변환한다. 요소와 텍스트 순서 및 공백이 보존되고 주석은 제외된다. 원본 DOM은 그대로이며 필수 노드 누락은 오류가 된다. |
| P1-02 | DOM 생성 · FR-002 | `toDOM`으로 지원하는 정규화 VNode를 생성한 뒤 `fromDOM`으로 다시 읽으면 같은 값이 나온다. 중첩 요소, 혼합 텍스트·공백, `<br>`, 빈 자식 목록, HTML 속성과 별개인 input 현재 값·체크 상태를 포함한다. 생성 노드는 기존 화면에 붙지 않고 입력 VNode는 변하지 않는다. |
| P1-03 | Diff · FR-003 | 추가, 삭제, 교체, 텍스트 변경, 속성 설정·제거를 각각 넣고 기대한 작업과 경로가 나오는지 확인한다. 동일 트리는 빈 목록이며 입력 트리 둘 다 그대로다. |
| P1-04 | Patch · FR-004 | 여러 변경을 적용한 뒤 DOM을 다시 읽어 목표 트리와 비교한다. 대상 외 형제와 컨테이너에 저장해 둔 Node 참조를 `===`로 비교한다. |
| P1-05 | 경로 안정성 · FR-003–004 | 한 부모에서 꼬리 자식 두 개를 삭제하면서 앞쪽 형제의 중첩 텍스트를 갱신한다. 반대 방향으로도 적용해 자식 두 개가 순서대로 추가되는지 확인한다. |
| P1-06 | 위치 기반 비교 · FR-003–004 | 동일 태그 리스트 `[A, B]`를 `[X, A, B]`로 바꾼다. 표시 순서는 새 트리와 같고 첫 번째 Node 참조는 그 위치에서 재사용된다. |
| P1-07 | input · FR-001–004 | `<input value="안녕">`의 `.value`만 `정글`로, 별도 체크박스의 `.checked`만 `false`로 바꿔 스냅샷을 만든다. 두 HTML 기본 속성은 보존되고, 이전 트리에 Patch하면 기존 노드의 현재 값과 체크 상태가 바뀐다. 속성과 현재 값이 함께 바뀌는 경우에는 속성을 먼저 적용해도 최종 프로퍼티가 목표 값과 일치한다. |
| P1-08 | 부분 쓰기 · FR-004 | 텍스트 하나를 바꿀 때 해당 텍스트의 변경만 기록되고, 동일 상태 적용에는 기록이 없다. |
| P1-09 | 입력 검증 · FR-006–007 | 깊게 중첩된 `onclick`, `script`, 지원 밖 속성·input 타입을 각각 입력한다. 오류가 보이고 실제 영역, 마지막 유효 미리보기와 이력이 유지된다. |
| P1-10 | HTML 경계 · FR-005–006, FR-009 | 빈 초안, 최상위 요소 여러 개, 엔티티, `a<!-- 주석 -->b`를 적용한다. 이력을 왕복한 뒤 다시 Patch해도 새 변경이 없다. |
| P1-11 | 경로 필터 · FR-001, FR-003–004 | DOM fixture로 `<div><!-- keep --><p>Hello <strong>Jungle</strong>!</p></div>`를 만들고 `strong` 뒤의 `!`만 `?`로 바꾼다. 주석이 섞여 있어도 해당 텍스트만 수정되고 `strong` 노드와 앞쪽 공백이 유지된다. |
| P1-12 | 동등한 초안 · FR-003–004, FR-007 | `<p class="note" title="x">&amp;</p>`를 `<p title="x" class="note">&#38;</p>`로 고친 뒤 Patch한다. Diff가 비어 있고 실제 DOM 쓰기와 이력 추가가 없다. |

P1-08에서는 초기 렌더 후 실제 영역에 `MutationObserver`를 연결하고 `subtree`, `childList`, `attributes`, `characterData`를 관찰한다. 동기 Patch 직후 `takeRecords()`로 변경 대상과 종류를 확인한다. 입력 컨트롤의 프로퍼티 변경은 P1-07에서 직접 읽어 확인한다. [DOM Standard · MutationObserver](https://dom.spec.whatwg.org/#mutation-observers)

## 2. Phase 1 브라우저 인수 테스트

| ID | 절차 | 합격 기준 |
| --- | --- | --- |
| P1-E1 · FR-005–007 | 페이지를 열고 샘플 텍스트 하나를 수정한다. 미리보기를 확인하고 Patch를 누른다. | 로드 직후 두 영역 내용이 같다. 편집 중에는 미리보기만 변하고, Patch 후 두 영역이 일치하며 이력이 한 칸 늘어난다. |
| P1-E2 · FR-007–009 | A → B → C를 적용한다. 뒤로 가서 B에서 수정 없이 Patch를 누른 후 앞으로 간다. | B와 C에서 실제 영역, 편집기, 미리보기가 같은 상태를 보여준다. B의 빈 Patch 이후에도 C로 갈 수 있다. |
| P1-E3 · FR-007–009 | C에서 B로 돌아가 D를 적용한다. 뒤로 가거나 앞으로 간다. | 탐색 경로는 A → B → D다. 처음과 끝에서 해당 탐색 버튼이 비활성화된다. |
| P1-E4 · FR-006, FR-009 | 편집기 내용을 바꾸되 Patch는 누르지 않고 이력을 이동한다. | 미적용 초안이 선택한 이력 상태로 대체된다. |
| P1-E5 · FR-006–009 | B에서 C로 갈 수 있는 상태로 돌아간 뒤 유효하지 않은 초안을 적용한다. | 오류 안내가 보인다. 실제 영역은 B이고 C로 이동할 수 있다. |
| P1-E6 · FR-005–009 | 키보드로 편집기와 세 버튼을 조작해 수정과 복원을 수행한다. | 편집기에 이름이 있고 현재 사용할 수 있는 버튼을 키보드로 조작할 수 있다. |
| P1-E7 · FR-006–009 | A → B를 적용하고 A로 돌아간다. 유효한 초안 C를 입력해 미리보기에 띄운 뒤 미허용 속성을 추가하고 Patch를 누른다. 이어서 앞으로 가기를 누른다. | 실패한 Patch 직후 실제 영역은 A, 미리보기는 C이고 오류가 보인다. 앞으로 가면 실제 영역·편집기·미리보기가 B로 복원되고 오류가 사라진다. |
| P1-E8 · FR-006, FR-009 | HTML 편집기에서 입력값을 `안녕`에서 `정글`로 수정한 뒤 Patch하고, 뒤로·앞으로 이동한다. | 미리보기는 수정 즉시 `정글`을 표시하고 실제 영역은 Patch 이후 `정글`을 표시한다. 이력을 이동하면 두 영역에서 `안녕`과 `정글`이 각각 복원된다. |

이번 주 완료 기준은 Phase 1 단위·통합 테스트와 브라우저 인수 테스트의 통과다. 검증 기록에는 브라우저와 버전, 실행 방법, 실패한 케이스를 남긴다.

## 3. Phase 2에서 추가할 테스트

| 범위 | 핵심 검증 |
| --- | --- |
| FunctionComponent · FR-010–012 | 최초 마운트 후 props가 자식에 전달되고, 자식의 콜백이 루트 갱신으로 이어진다. |
| useState · FR-013–016 | Hook을 두 번 호출해 각각 다른 값을 둔다. 하나를 변경해도 다른 슬롯이 유지되고 바뀌지 않은 DOM의 참조가 유지된다. |
| useEffect · FR-017 | 첫 실행에서 이미 반영된 DOM을 읽을 수 있다. 같은 의존성에서는 다시 실행되지 않는다. 의존성을 바꾸면 `cleanup → effect` 순서를 확인한다. |
| useMemo · FR-018 | 계산 호출 횟수를 세어, 의존성이 같으면 재사용하고 하나라도 바뀌면 다시 계산하는지 확인한다. |
| 루트 상태 · FR-019–020 | 하나의 상태를 두 자식이 표시하고, 자식 쪽 클릭 한 번으로 두 표시가 같은 값으로 바뀐다. |
| Batching · FR-021 | 선택 구현 시 연속 setter 이후의 최종 상태와 DOM 반영 횟수를 함께 확인한다. |

## 4. 선택 성능 검증

같은 샘플에서 텍스트 하나를 바꿀 때 전체 교체와 부분 갱신을 비교한다. 먼저 노드 재사용 여부와 DOM 변경 범위를 기록한다. 실행 시간까지 비교할 경우 브라우저와 입력을 고정해 여러 번 측정하고, Diff 계산 시간과 브라우저의 Layout·Paint 구간을 나눠 본다.
